# Build plan

What the Opus build chats do, in dependency order, from the first commit of the new repository to cutover, then the hardening the Oct 18 audit asked for (M7) and the features Matt picked for real-world use (M8), then the Oct 18 review's fixes (M9), the study layer v1 (M10) and Captions for the E.V. tab (M11). No dates: each task opens when the one it depends on is done.

## Repository layout for the initial commit

A new repository, `miura5/ev4`, private. The layout is the architecture made visible: anything that executes is under `core/`, `scripts/` or `page/`; anything that describes is under `spec/`; anything that proves is under `test/`.

```
ev4/
  CLAUDE.md                 orientation + the build-chat contract (next section)
  README.md                 what E.V. is, where things live, no secrets
  package.json              node:test, playwright for the harness, nothing else
  spec/
    ev.spec.json            collections (class, writer, key, schema), tasks, environments,
                            capacity, pipelines (step lists), boundaries, working agreements,
                            ui, persona, jobs, release
    schemas/<collection>.schema.json   one JSON Schema per collection
  core/
    evcore.mjs              pure rules; VERSION = the release tag
    cli.mjs                 run protocol, steps, build-chat commands (lint, rebuild, seed-staging,
                            deploy, verify-deploy, migrate, verify-migration, verify-writes)
    migrate.mjs             migrations keyed by collection and schema version
    validate.mjs            schema validation shared by cli and the page
  scripts/canvas/           dates.js, files.js, texts.js, poll.js: browser scripts as files
  page/
    index.src.html          the shell
    app.js, styles.css      page logic and look; core.js and spec.json are build outputs
  studywatch/
    reader/                 the MCP extension (v2 tools), tests beside it
    app/                    the Swift app, unchanged from v3
  tools/
    build.mjs               dist/: page files, manifest.json, system docs, task prompts
    prompts.mjs             renders every task prompt from spec.tasks and the step lists
  test/
    core.test.mjs, cli.test.mjs, schema.test.mjs, prompts.test.mjs, migrate.test.mjs,
    parity.test.mjs, reader.test.mjs
    harness/run.cjs, stub.js, data/
  fixtures/                 gitignored: record exports, backups, anything personal
  dist/                     gitignored build outputs
```

Two rules about the layout itself: nothing under `fixtures/` or `dist/` is ever committed (a test greps the tree for record exports and session files), and `scripts/canvas/` holds the only code that runs outside the repository's own runtime — in Matt's browser — so it is reviewed as carefully as `core/`.

## The build-chat contract (CLAUDE.md for v4)

The first commit's CLAUDE.md is the contract every Opus chat works under. Its substance, in the order a chat meets it:

1. **Start.** Read `spec/ev.spec.json`, this doc's Build plan tab, and the v3 doc's Board. Run `node core/cli.mjs verify-deploy staging` and read its answer before touching anything. Take the lowest open backlog task whose dependencies are done; say which.
2. **Scope.** A task is one backlog id. Anything the task needs that the spec's shape, a schema or this doc does not provide goes back to a design chat as a question, not into the code. Code-level choices are the build chat's.
3. **Prove.** `npm test` green, then the task's definition of done exactly as written. Where a pipeline is involved, the proof is a scheduled task fired against staging and its `runs/<id>` read back — never a hand replay of the steps. Where the page is involved, the harness at phone and desktop width and a look at the screenshots.
4. **Ship.** Commit with the task id first in the message and the attribution lines; push; `build`; `deploy staging` and run every printed call; `verify-deploy staging` green. Live deploys only on Matt's explicit OK, by the same printed calls.
5. **Record.** A Board row per task (status, one line), a Changelog line per deploy, a Decision only when the design chat says so. Never a date on anything. The environments registry gains a row only from a diagnostic run's id.
6. **Safety.** The v3 hard limits unchanged: no graded work, no patient identifiers, Canvas read-only, nothing deleted anywhere, no passwords, nothing posted as Matt, the journal never read by anything but the page. Matt's explicit OK for: publishing the live page, creating or changing a Mac-bound task, reading the journal. A refused action is reported, never worked around.
7. **Gotchas carried from v3,** each with its rule: the run safety review refuses fetched code (run the checkout); a scheduled task inherits its creating chat's repository and Mac link (create tasks from the right chat); `javascript_tool` stops at 45 s and the bridge cuts \~250 KB (start, poll, collect); a partial `capabilities` wipes the rest (deploy prints it whole); `update` merges nested maps (Edits are replaced whole); fake time in the harness races (`setSystemTime` plus condition waits).

**Definition of done, the general form.** A task is done when: its tests exist and pass; its proof ran as written; `verify-deploy staging` is green afterwards; its Board row says so; and nothing it touched is outside its id's scope. A task that cannot meet its proof is not done and says why on its Board row.

## Parity, cutover and the v3 sunset

v3 keeps running, untouched, through every milestone. Cutover is one evening's procedure, rehearsed on staging first, with the v2 → v3 cutover as the model.

1. **Parity (M5).** `seed-staging` from a fresh live export; both cores run nightly on it from a build chat (`parity.test.mjs`): the same plan, the same review set, the same recomputed states. Disagreements are bugs in v4 or documented improvements with a Decision; the gate is a week with neither.
2. **Rehearsal.** The full cutover below, run against staging as if it were live, including `verify-deploy` and the first fired runs.
3. **Freeze.** Matt's OK. The v3 morning and evening tasks run one last time; `evening-mac` writes the final v3 backup.
4. **Migrate.** `migrate v3` on a live export taken after that evening; `verify-migration` zero mismatches; the batches applied to the live record; every v3 original kept under `legacy/` with `migratedTo`.
5. **Deploy live.** `deploy live` and its printed calls: `system/manifest` and `system/spec`, the page with its files and capabilities, the live tasks created from the right chats (cloud from a repository chat, `evening-mac` from a Mac-linked chat with the one folder). `verify-deploy live` green.
6. **Sunset v3.** Its tasks disabled and kept (`spec.tasks.retired` in v4 lists them with the reason); `ev-core` archived read-only; its doc's Board gets one closing row and its Changelog one final line pointing here. Nothing is deleted.
7. **First runs.** The next morning and evening runs are read back from `runs/`; `watchdog` is live; the greeting that morning mentions the new release once.
